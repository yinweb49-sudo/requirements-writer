# requirements-writer

一个**与项目解耦**、面向 vibe coding 的 Agent Skill：先帮助普通用户或产品经理把业务结果说清楚；从无到有且有界面时，用可交互视觉原型建立沟通锚点；把复杂任务拆成工作量与上下文可控的 AI 执行单元，并按项目策略建立安全的代码恢复锚点。

Skill 会按风险选择轻量、标准或审计模式，把用户原话、代码事实和外部资料整理为可追溯证据，再用“当前决策台账”固定真正指导开发的结论。每期限制为一个主要问题，带场景化验收、阶段交接和按授权执行的 Git 检查点。

**文档一次写完，施工分段放行。** 用户确认原型是跨会话的长动作，需求文档不为它停笔：主需求文档和期 0 到期 N 的全部期次一次性写到位，未经视觉验证的结论标注“待视觉确认复核”。真正被拦住的是代码施工——期次序列上划出一条**视觉确认门槛线**，门槛线之前是前端可见效果，之后是后端、数据、鉴权和迁移；原型期文档写明启动命令、本地预览地址和请用户走的测试路径，用户实测确认、修改闭环、后续期次复核之后，才开始后端施工。

## 核心设计：通用引擎 + 项目档案

- **通用引擎**（本仓库全部内容）：方法论和模板，不含任何具体项目的路径、术语、端口。
- **项目档案**（`requirements-profile.md`，留在你自己的项目里）：一次性声明本项目的架构分层、数据库、鉴权 / 白名单、验收方式、结构检索工具、样本文档路径。
- **分级证据档案**：轻量需求只保留关键原话；标准 / 审计模式保留完整需求证据、强调、否定和冲突。真实敏感信息始终脱敏，不因逐字保真进入仓库。
- **两种触发场景**：新对话按文档强度收录；开发中途提需求时使用「需求起点锚点 + 前序候选 + 与已有文档对账」，避免把调试噪音混成需求。
- **当前决策台账**：原话负责举证，当前有效的 `D-xxx` 才指导开发；旧决定保留历史和替代关系，不让过期原话覆盖用户的新确认。
- **编号追溯与销账**：需求、代码事实、决定和期次使用 `U/P/A/E/D` 编号；标准 / 审计模式做到零“无归属”，纯寒暄或调试指令可标“非需求上下文”。
- **业务共识**（每份主需求文档开头必写）：用大白话保留用户原始诉求，说明 AI 当前理解的最终效果，并显式列出多轮沟通中的变化和冲突；重大冲突未确认前不拆期。原话前后矛盾时把两端原话原样贴给用户直接选，AI 不得替用户取舍，不得用含糊表述掩盖分歧。
- **范围闸门**（每次需求单独判断）：每项功能、技术改动和期次都要有明确需求或必要配套依据；模板示例和可选设想不自动进入开发范围。
- **视觉先行**（从无到有且有界面时强制）：先写最小业务草案，再用正式前端代码 + 可替换 mock 做可交互原型；用户确认必须绑定提交号或版本、页面入口和截图 / 录屏。必要时先做最小期 0 技术探针，但探针后仍回到视觉原型。
- **确认门槛只拦施工**：全部期次一次写完，用视觉确认门槛线区分“可立即施工”和“确认并复核后施工”；原型期必写“本地预览与用户确认”（启动命令、预览入口、用户测试路径、放行条件）。等待确认期间不重写需求，避免文档搁置和上下文膨胀。
- **确认后复核**：用户在原型上说的新话回写证据与决策后，逐条复核门槛线之后已写好的期次——无实质变更原样执行，有实质变更先改文档再施工，被推翻则作废重拆。
- **AI 执行分期**（每次拆期必做）：按变更面、跨层依赖、不确定性、数据安全风险、验收复杂度和上下文负载评分，普通开发期控制在 4–7 分，过重强制拆、过轻合理并。
- **上下文接力**（跨窗口开发）：每期只加载核心材料，遇阻填写快照，完成后把业务事实、关键实现、验收结果和下一期前置条件写入阶段交接。
- **Git 代码检查点**：按项目档案选择不保存、本地提交、本地标签或远程分支；远程存在不等于允许推送。阶段标签只恢复代码，不冒充数据库或外部状态回滚。
- **敏感信息硬门槛**：真实密码、令牌、私钥和带口令连接串一律阻止进入 Git，不提供“允许上传到私有库”的选项。

skill 运行时先读项目档案，把模板里的占位符（`{{前端}}`、`{{本地后端}}`、`{{云端后端}}`、`{{主库}}`、`{{次库}}`、`{{鉴权方案}}`、`{{白名单机制}}`、`{{验收方式}}`、`{{结构检索工具}}`）替换成真实值。**项目里不存在的层 / 库 / 机制会被自动裁剪掉，不会硬套三层架构。**

## 维护与发布策略

- 本仓库当前由单一维护者维护。
- 后续用户明确要求“发布 / 同步到 GitHub”时，默认直接提交并推送到 `main` 主分支，不默认创建功能分支或 Pull Request。
- 只有用户明确要求代码评审、草稿 PR 或隔离开发时，才使用独立分支和 Pull Request。
- 主分支推送成功后，再同步本机安装目录并运行 Skill 校验，保证本地使用版本与 `main` 一致。
- 如果分支保护或权限阻止主分支推送，停止并说明原因；禁止用强推绕过保护。

## 安装

skill 的加载目录取决于你的 Agent 工具（Claude Code / Codex 等）。常见三种方式：

### 方式 A · 用户级全局（自用多项目最省事）

放到用户级 skills 目录，所有项目自动可见：

```bash
git clone https://github.com/yinweb49-sudo/requirements-writer.git \
  ~/.claude/skills/requirements-writer
```

> Windows PowerShell：`git clone <url> "$env:USERPROFILE\.claude\skills\requirements-writer"`
> 有的工具用 `.agents/skills/` 或 `.codex/skills/`，按你的工具约定放。

### 方式 B · 作为项目子模块（团队 / 多机、版本可控）

```bash
git submodule add https://github.com/yinweb49-sudo/requirements-writer.git \
  .claude/skills/requirements-writer
git pull --recurse-submodules   # 后续拉更新
```

### 方式 C · 下载压缩包解压（一键装，不用 git）

从仓库 Releases 或 `Code → Download ZIP` 下载，解压到 skills 目录即可。

## 使用（三步）

1. **建项目档案**：复制 `references/project-profile-template.md` 到你的项目仓库根（或 `.agents/`），改名为 `requirements-profile.md`，按提示填空。可参考 `examples/example-profile.md`（虚构示例）。
2. **触发 skill**：让 AI“按 requirements-writer 编写 XX 功能的开发需求文档 / 分期开发提示词”。
3. skill 自动读档案 → 选择文档强度 → 建立需求证据与当前决策 → **一次性写完主需求文档和期 0 到期 N 的全部提示词**（有新界面时在期 1 之后划出视觉确认门槛线）→ 施工原型并唤起本地预览交用户实测 → 确认后回写决策、复核后续期次并升为 v1.0。

产出结构：

```text
docs/<功能名称>/
├── 00-需求证据与原话参考.md        # 标准 / 审计模式的历史证据，不是最终执行基线
├── <功能名称>-开发需求文档.md      # v0.9 待视觉确认基线 → v1.0 已确认开发基线
└── 开发提示词/
    ├── README.md                   # 期次总览里标出视觉确认门槛线
    ├── 期0-技术探针.md              # 仅技术事实阻塞视觉成立时
    ├── 期1-前端原型与视觉确认.md    # 从无到有且有界面时必须，含本地预览确认门槛
    └── 期N-*.md                    # 门槛线之后的后端 / 数据 / 集成期，与前端期一次写完
```

> 项目没建档案也能用：skill 会退而读 `CLAUDE.md` / `README.md`，再不行就问你几个关键问题。建档案只是让它一次到位、不用每次追问。
