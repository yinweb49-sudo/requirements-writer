# 分期开发 Git 备份工作流

生成或评审分期开发提示词时必须使用本工作流。Git 备份是每期验收后的完成门槛，不是产品功能，不单独拆成开发期，也不因此扩大业务范围。

## 一、编写分期文档前：判断 Git 云端备份是否可用

在项目仓库中执行只读检查，不凭目录名、`.git` 文件是否存在或文档描述猜测：

1. 用 `git rev-parse --show-toplevel` 确认当前目录属于 Git 工作区。
2. 用 `git symbolic-ref --short HEAD` 确认当前处于具名分支，不是 detached HEAD。
3. 用 `git remote` 和 `git remote get-url <远程名>` 确认存在目标远程；默认优先 `origin`，用户或项目已有约定优先。
4. 用 `git ls-remote --exit-code <远程名>` 验证当前环境能访问远程。
5. 在确定项目的 Git 钩子不会产生外部副作用时，用 `git push --dry-run --porcelain <远程名> HEAD` 验证当前身份具备推送能力且分支可推送。不能安全执行时，把写权限标为“待首次备份验证”，不要伪装成已验证。
6. 用托管平台已有的只读 CLI / API 查询远程仓库可见性；无法可靠查询就记为“未知”，不得根据 URL、仓库所有者或用户口头提到“通常是私有库”自行推断。
7. 读取当前分支、上游分支和工作区状态。只记录状态，不在编写文档阶段提交、推送、改远程或改分支。

不得把含用户名、令牌、密码或查询参数的远程 URL 原样写进需求文档、提示词或对话。只记录脱敏后的托管平台、仓库标识、远程名和分支；无法安全脱敏时只写远程名。

按检查结果记录以下状态：

| 状态 | 判定 | 分期文档处理 |
|---|---|---|
| 可用 | Git 工作区、具名分支、目标远程、远程访问均正常，且推送权限已验证 | 为每一期加入完整备份步骤 |
| 写权限待验证 | 前四项正常，但无法安全验证推送权限 | 加入完整备份步骤，并要求首次备份先验证推送；不得写成“已连接完善” |
| 不可用 | 不在 Git 仓库、没有目标远程、远程不可访问、detached HEAD 或明确没有推送权限 | 记录原因；不自动初始化仓库、创建云端仓库、改远程或索要凭据 |

生成 `开发提示词/README.md` 时固化检查日期、状态、远程名、当前分支、脱敏仓库标识和失败原因。每期开始时重新做简短检查；若仓库或远程状态变化，以现场结果为准并同步 README。

## 二、在分期 README 中保存备份与授权状态

加入“Git 备份基线”表，至少包含：

```markdown
## Git 备份基线

| 项目 | 当前值 |
|---|---|
| 文档生成时检查时间 | YYYY-MM-DD HH:mm（时区） |
| Git 云端备份状态 | 可用 / 写权限待验证 / 不可用 |
| 远程与分支 | <远程名 + 脱敏仓库标识 + 分支；不得含凭据> |
| 远程可见性 | 私有 / 公开 / 未知 |
| 不可用原因 | 无 / <可验证原因> |
| 阶段标签规则 | `backup/<feature-slug>/phase-N` |
| 敏感信息云端备份授权 | 未触发 / 已允许 / 已拒绝 / 已撤销 |
| 授权范围 | 当前仓库 + 当前远程 + 本功能全部期次 |
| 授权时间与依据 | 未触发 / YYYY-MM-DD HH:mm，用户明确回复 |
```

`<feature-slug>` 必须使用适合 Git ref 的稳定短名，只含小写字母、数字和连字符。文档编写时没有触发敏感信息风险，就把授权状态写为“未触发”，不要提前询问用户。

在 README 的“期次总览”中预先写好各期阶段标签和计划状态。实际备份结果以远程阶段标签和交付报告为准，精确提交号可随时通过 `git rev-parse <阶段标签>` 查询。不要为了把提交号或“已推送”状态写回被标记的同一个版本而制造循环提交；后续正常开发本来就要修改 README 时再同步历史状态。

## 三、每期开始：保护用户原有改动

1. 重新确认仓库、远程、当前分支和备份状态。
2. 记录起点提交 `BASE_SHA` 和期初 `git status --short`。
3. 把期初已有的未提交改动视为用户资产。不得覆盖、丢弃、还原或偷偷并入本期备份。
4. 如果期初改动与本期目标文件重叠，先说明影响；只有无法安全区分时才请求用户处理。

## 四、每期验收后：先检查敏感信息

只在本期任务和验收通过后执行备份。提交前检查本期将要提交的已修改、已暂存和未跟踪文件；推送前再检查本次待推送提交。优先使用项目已经配置的 secret scanner；项目没有时，至少检查文件名和差异内容中的高风险线索。

重点包括但不限于：

- `.env`、凭据文件、云服务账号文件、密码库、Cookie / Session 导出；
- API Key、Access Token、刷新令牌、数据库密码、连接串中的口令；
- SSH / PGP / TLS 私钥、助记词、签名密钥和证书私钥；
- 带认证信息的远程 URL、配置文件、日志、测试夹具或截图；
- 本期新增但被 `.gitignore` 漏掉的本地私密配置。

不要在提示、日志、文档或交付报告中回显敏感值。只报告文件路径、敏感类型、目标远程可见性和处理建议。示例占位符、脱敏样例和 `.env.example` 不能只凭文件名判定为真实密钥，应结合内容确认。

如果敏感信息此前已经进入 Git 历史或云端，明确提示“删除当前文件不足以消除泄露”，建议旋转 / 吊销凭据，并把历史清理作为需要用户确认的高风险动作；不得擅自改写历史或强推。

## 五、敏感信息上传：只询问一次并持久化决定

检测到本期待备份内容含真实或高度疑似敏感信息时，先读取分期 README 的授权状态：

### 状态为“未触发”

暂停提交和推送，只向用户询问一次。提示必须包含：

- 检出的文件路径和敏感类型，不展示具体值；
- 远程仓库是私有、公开还是无法确认；
- 一旦推送会进入云端和 Git 历史，后续只删除文件通常不能彻底清除；
- 授权范围是“当前仓库 + 当前远程 + 本功能全部期次”。

明确询问用户是否允许把这些敏感文件随阶段备份上传。

### 用户明确允许

1. 把 README 状态更新为“已允许”，记录时间、脱敏远程标识和用户明确回复；不得记录敏感值。
2. 继续本期提交与推送。
3. 后续期次只要仓库和远程未变，直接沿用授权并上传，不再重复询问。

### 用户拒绝

1. 把 README 状态更新为“已拒绝”。
2. 不提交、不推送真实敏感文件；先将其排除、脱敏或改为安全样例，再备份其余安全改动。
3. 后续期次沿用拒绝状态，不重复询问；发现敏感文件时继续阻止其上传。
4. 不擅自删除用户文件、改写历史或替用户旋转密钥。

### 重新确认的唯一条件

仅当用户主动撤销 / 修改授权，或目标仓库、目标远程、仓库可见性发生变化时，把旧授权视为失效并重新确认。切换开发窗口、进入下一期、出现同类新敏感文件，都不构成重复询问理由。

## 六、完成阶段备份

敏感信息检查与授权处理完成后：

1. 使用本期动手前已经记录的 `BASE_SHA` 和期初工作区清单核对变更；不得在收尾时重新计算起点来掩盖期中改动。
2. 按 `references/phase-workload-planning.md` 填完本期“阶段交接记录”，让下一窗口不依赖聊天记忆，并将交接记录纳入本期提交。
3. 用明确文件路径暂存本期改动；禁止用 `git add .`、`git add -A` 把无关改动一起提交。
4. 复核暂存清单和差异，确认没有用户期初改动、范围外文件或未获允许的敏感信息。
5. 创建阶段提交，提交信息使用 `backup(<feature-slug>): phase N complete`。
6. 创建不可覆盖的附注标签 `backup/<feature-slug>/phase-N`。
7. 推送当前分支；没有上游分支时，在首次成功推送时建立上游。
8. 单独推送阶段标签，并通过远程查询确认分支提交与标签均已存在。
9. 交付报告写明：验收结果、分支、完整提交号、阶段标签、推送结果、未备份文件和原因。

同名标签已存在时不得删除、强制移动或覆盖：

- 若标签已指向本期同一提交，直接复用。
- 若指向不同提交，创建递增修订标签，例如 `backup/<feature-slug>/phase-N-r2`，并在交付报告说明。

没有代码变化但本期确已完成验收时，不制造空提交；可在用户认可当前提交就是该期结果的前提下给现有提交创建阶段标签。

文档生成时已经判定为“不可用”，且本期开始重新检查后仍不可用时，记录“本期未执行云端备份”及原因，可以完成开发交付，但不得声称已有云端恢复点，也不得自动创建或连接远程。

原本状态为“可用 / 写权限待验证”但实际推送失败时，不得宣称本期“完整完成”。保留已通过的开发和验收结果，标记为“开发验收通过，云端备份失败”，说明错误并修复备份后再进入下一期。禁止用强推绕过非快进、分支保护或权限问题。

## 七、安全回滚方式

阶段标签是精确回滚锚点。需要回看或恢复时，优先新建分支，不覆盖当前工作区：

```bash
git fetch <远程名> --tags
git switch -c rollback/<feature-slug>-phase-N backup/<feature-slug>/phase-N
```

除非用户明确要求并确认未提交改动已妥善保存，不使用 `git reset --hard`、强推或删除分支 / 标签。
