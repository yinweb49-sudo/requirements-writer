# 分期开发 Git 代码检查点工作流

本工作流为每期建立可核对的代码恢复锚点。它不是产品功能，也不代表数据库、生产数据或第三方状态已经回滚。

## 目录

1. 保存策略与授权
2. 编写分期文档前的只读检查
3. 每期开始保护用户改动
4. 敏感信息硬门槛
5. 完成代码检查点
6. 远程备份
7. 代码恢复与数据回退

## 一、保存策略与授权

从项目档案读取保存策略：

| 模式 | 行为 |
|---|---|
| 不保存 | 只完成开发与验收，不创建提交或标签 |
| 本地提交 | 精确暂存本期文件并创建本地提交 |
| 本地标签 | 创建本地提交和不可覆盖阶段标签 |
| 远程分支 | 在本地标签基础上，推送到已明确授权的远程和分支 |

Git 不可用或当前目录不是仓库时，记录“Git 不可用”，不得擅自初始化仓库。当前任务按“不保存”执行，只记录期初 / 期末文件清单与 SHA-256 用于核对；这些哈希不是恢复备份。若确实需要代码恢复能力，先取得用户授权，再选择初始化版本控制或项目批准的备份方式。

远程存在、可以访问、凭据可用或仓库是私有库，都不等于用户授权推送。只有以下任一条件成立时才能执行远程写入：

- 用户在当前任务中明确要求提交、备份或推送到指定远程。
- 项目档案记录了团队批准的自动推送策略、目标远程和分支规则。

授权只覆盖用户点名的仓库、远程、分支和任务范围。仓库、远程或可见性变化时重新确认。没有授权时降级为本地提交 / 标签，不把远程失败当作开发失败。

## 二、编写分期文档前的只读检查

1. `git rev-parse --show-toplevel`：确认 Git 工作区；失败时按上面的“Git 不可用”分支记录并停止后续 Git / 远程检查。
2. `git symbolic-ref --short HEAD`：确认具名分支。
3. `git remote`、`git remote get-url <远程名>`：确认远程；不得回显含凭据 URL。
4. `git ls-remote --exit-code <远程名>`：只读验证访问。
5. 只有已获得远程写入授权，且确认钩子不会产生外部副作用时，才用 `git push --dry-run --porcelain` 检查推送条件。
6. 用托管平台只读 CLI / API 查询可见性；无法可靠判断时写“未知”。
7. 记录当前分支、上游、HEAD 和工作区状态，不在文档生成阶段提交、推送或改远程。

在分期 README 中记录：

```markdown
## Git 代码检查点基线

| 项目 | 当前值 |
|---|---|
| 检查时间 | YYYY-MM-DD HH:mm（时区） |
| 保存策略 | 不保存 / 本地提交 / 本地标签 / 远程分支 |
| 本地 Git 状态 | 可用 / 不可用 |
| 远程访问状态 | 未检查 / 可访问 / 不可访问 |
| 远程写入授权 | 未授权 / 已授权（依据与时间） |
| 远程与分支 | <仅已授权时填写脱敏标识> |
| 远程可见性 | 私有 / 公开 / 未知 |
| 阶段标签规则 | `checkpoint/<feature-slug>/phase-N` / Git 不可用时“不适用” |
| 数据 / 外部状态回退 | 不涉及 / 见 <方案路径> |
```

`<feature-slug>` 只含小写字母、数字和连字符。

## 三、每期开始：保护用户原有改动

1. 重新确认仓库、当前分支、保存策略和授权状态。
2. 记录起点提交 `BASE_SHA` 和期初 `git status --short`。
3. 把期初已有未提交改动视为用户资产，不得覆盖、还原、丢弃或偷偷纳入本期提交。
4. 期初改动与目标文件重叠时先判断能否安全区分；无法区分才请求用户处理。
5. 禁止用 `git reset --hard`、`git checkout --`、强推或移动旧标签清理工作区。

## 四、敏感信息硬门槛

验收后、提交前检查本期修改、暂存、未跟踪文件和待推送提交。优先使用项目已有 secret scanner；没有时至少检查高风险文件名和差异内容。

重点检查：

- `.env`、凭据文件、云账号文件、Cookie / Session 导出；
- API Key、访问令牌、刷新令牌、密码和带口令连接串；
- SSH / PGP / TLS 私钥、助记词、签名密钥；
- 带认证信息的 URL、日志、测试夹具、截图和需求原话档案；
- 未被 `.gitignore` 排除的本地私密配置。

处理规则：

1. 真实或高度疑似敏感信息一律阻止提交和推送；不提供“用户授权后继续上传”选项。
2. 只报告文件路径和敏感类型，不展示具体值。
3. 将配置改为环境变量、秘密管理服务或脱敏样例；只备份安全改动。
4. 不擅自删除用户文件、轮换凭据或改写 Git 历史。
5. 敏感信息已进入历史或远程时，说明删除当前文件不足以消除泄露，建议立即吊销 / 轮换；历史清理和强推必须另行获得高风险授权。

## 五、完成本地代码检查点

保存策略不是“不保存”时：

1. 用动手前记录的 `BASE_SHA` 和期初工作区清单核对变化。
2. 填完阶段交接记录并纳入本期提交。
3. 用明确文件路径精确暂存；禁止 `git add .` 和 `git add -A`。
4. 复核暂存文件和差异，确认没有期初用户改动、范围外文件或敏感信息。
5. 创建提交：`checkpoint(<feature-slug>): phase N complete`。
6. 保存策略包含标签时，创建不可覆盖附注标签：`checkpoint/<feature-slug>/phase-N`。
7. 同名标签指向当前提交时复用；指向其他提交时创建 `phase-N-r2` 等递增修订标签，不删除或移动旧标签。
8. 没有代码或文档变化时不制造空提交；只有用户认可当前提交代表该期结果时，才给现有提交加标签。

## 六、远程备份

只有保存策略为“远程分支”且远程写入已授权时执行：

1. 再次确认目标远程、分支和可见性没有变化。
2. 推送当前已授权分支；需要建立上游时只对该分支执行。
3. 单独推送阶段标签。
4. 用远程查询验证分支提交与标签均已存在。
5. 交付报告写明验收结果、分支、完整提交号、阶段标签、推送结果，以及未备份文件和原因。

推送失败时保留本地成果，状态写为“开发验收通过，本地检查点完成，远程备份失败”。不得强推绕过非快进、分支保护或权限问题。

## 七、代码恢复与数据回退

阶段标签只是代码恢复锚点。安全回看时优先新建分支：

```bash
git fetch <远程名> --tags
git switch -c restore/<feature-slug>-phase-N checkpoint/<feature-slug>/phase-N
```

除非用户明确授权并确认未提交改动已妥善保存，不使用破坏性重置、强推或删除分支 / 标签。

涉及以下任一内容时，主需求文档和对应期次必须单独写回退或补偿方案：

- 数据库结构或生产数据迁移；
- 已发送消息、已扣费或已调用第三方产生的外部状态；
- 不可逆删除、权限变更和密钥轮换；
- 无法通过切回代码版本恢复的缓存、队列或文件格式变化。

不得用“已有 Git 标签”代替这些方案，也不得宣称代码标签能实现业务状态的精确回滚。
