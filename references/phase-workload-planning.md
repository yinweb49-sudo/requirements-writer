# AI 开发分期与工作量规划

生成或评审分期开发文档时必须使用本工作流。分期的首要目的，是把复杂开发任务拆成 AI 能在单个窗口内稳定完成、独立验收、随时中断恢复的小问题；不是按产品菜单、前后端层级或业务模块机械切块。

## 一、分期定义

把每一期视为一个 **AI 执行单元**：

- 只解决一个主要问题，允许包含为解决它不可缺少的配套任务。
- 完成后留下可验证的代码、测试、调研结论、接口契约或迁移结果。
- 开始条件、输入、依赖和完成标准明确，不依赖上一窗口的聊天记忆。
- 结束时系统处于可构建、可验证、可继续开发的安全状态，不留下无法运行的半成品。
- 与前后期有关联，但依赖通过代码、文档、阶段标签和交接记录传递。

一期不必单独形成完整的用户可见功能。只要它解决了独立技术问题、降低了后续不确定性，并且结果可以独立核对，就可以成为一期。不得为了“每期都有页面效果”把大量地基、接口、页面和测试塞进同一期。

## 二、拆期前准备

1. 从已准入范围中列出任务原子：现状调研、业务规则确认、契约设计、代码改动、数据变更、迁移、测试、清理和文档同步。
2. 标记每个任务原子的前置依赖、影响模块、未知信息、风险和验收方式。
3. 先画单向依赖顺序，再组合成候选期次；不要先按“前端期 / 后端期 / 优化期”命名后硬塞任务。
4. 对每个候选期次做六维评分，并在输出文档前完成拆分或合并。
5. 只有当现状不清会直接导致实现方向可能错误时，才创建调研 / 业务确认期。该期必须产出可引用的现状地图、证据、已确认决策和后续入口，不能只是“先看看代码”。

## 三、六维工作量评分

评分用于比较 AI 单窗口执行负担，不是人工工期或小时估算。每个维度记 0–2 分，总分 0–12。

评估从“读取核心材料、理解业务事实”一直到“实现、验收、填写交接并完成备份”的整期负担，不能只看预计代码量。调研、用户确认、跨模块检索、迁移验证和失败排查都属于工作量。

| 维度 | 0 分 | 1 分 | 2 分 |
|---|---|---|---|
| 变更面 | 仅文档 / 极小局部 | 一个聚焦模块或少量紧密相关文件 | 多模块、广泛文件或需要同步替换旧实现 |
| 跨层与依赖 | 单层、无新依赖 | 两层联动或复用一个稳定依赖 | 三层以上、新依赖、异步链路或跨项目协作 |
| 业务 / 技术不确定性 | 规则和代码入口已明确 | 需要聚焦阅读或少量确认 | 需要调研、第三方验证或会改变方案的用户决策 |
| 数据 / 安全 / 可逆性风险 | 无状态或容易回退 | 配置、数据格式或权限有局部变化 | 数据迁移、鉴权、计费、密钥、删除或难回退操作 |
| 验收复杂度 | 一个聚焦检查即可 | 多个成功 / 失败场景和直接回归 | 多环境、端到端、迁移回滚或长链路验证 |
| 上下文负载 | 一个局部模块和少量材料 | 多个相关模块 / 规范，需要持续对照 | 跨项目、大量历史材料或多个业务域同时进入上下文 |

评分后应用：

- **0–3 分：偏轻。** 单一期的小改动可以保留；多期方案中的轻量期原则上并入相邻期。
- **4–7 分：目标区间。** 作为普通开发期的推荐负载。
- **8–12 分：过重。** 输出文档前必须继续拆分，不能只标“高风险”后原样保留。

以下情况不看总分也要处理：

- 不确定性为 2：先完成聚焦调研 / 确认，或把未确认分支移出实现期。
- 数据 / 安全 / 可逆性风险为 2：不得与无关功能混在一期；迁移、鉴权、计费、密钥或删除要有独立验证与回退边界。
- 上下文负载为 2：按模块、契约或依赖顺序继续拆，并强化阶段交接。

## 四、拆分与平衡规则

按以下顺序选择边界，不要求全部使用：

1. **先认知再施工**：现状或业务规则不清时，先产出证据和决策，再进入编码。
2. **先固定契约再接入**：先稳定数据结构、接口契约或内部边界，再让调用方接入。
3. **先最小技术闭环再扩展**：先跑通一个可验证路径，再增加已确认场景。
4. **先新链路再迁移 / 清理**：新实现稳定后再迁移数据或删除旧体系。
5. **先低风险后高风险**：把不可逆、高权限或外部依赖操作隔离到可单独停下的一期。

每个普通开发期同时满足：

- 一个主要问题，标题直接描述要解决的问题。
- 3–6 个核心任务包；超过 6 个时重新判断是否混入多个问题。
- 有明确输入、输出、依赖、验收和“本期不做”。
- 完成后可构建 / 可运行 / 可检查，不把无法验证的半成品交给下一期。
- 后一期只依赖前一期的持久化产物，不依赖聊天记忆。

平衡全部候选期次：

- 普通开发期尽量都落在 4–7 分，最高分与最低分差不超过 3 分。
- 某一期 8 分以上时强制再拆；不能用“这是核心期”作为超载理由。
- 多期中的 0–3 分轻量收尾应并入相邻期，除非它是有独立价值的调研确认、数据迁移、破坏性清理或高风险验证检查点。
- 一个原子任务仍达到 8 分以上时，先拆出调研、契约、风险隔离或验证准备，再对剩余任务重新评分。
- 不为追求分数平均而增加范围外工作，也不创建没有独立产物的占位期。

不要按前端、后端、数据库机械分期。如果拆开后任一期无法独立验证或会使系统长期不可用，就按可验证契约或最小技术闭环重新组合。相反，只要边界稳定且可验证，同一项业务能力可以拆成多个技术执行期。

## 五、上下文边界

每期提示词都写清：

- **核心必读**：主需求文档中与本期直接相关的章节、上期交接记录、2–6 个最关键代码入口或规范。
- **按需读取**：只有出现指定问题时才读取的次要材料。
- **禁止泛读**：不要让执行 AI 为“了解全局”一次性加载全部仓库、全部历史需求或所有期次。
- **上下文负载结论**：低 / 中 / 高及理由；“高”必须重新拆分，不能直接进入开发。

主需求文档保存完整业务背景；单期提示词只摘录本期必须知道的已确认结论，并通过路径回指原文，不重复粘贴整份需求。

## 六、阻塞、恢复与动态拆期

每期在动手前列出可能改变方案的阻塞点和确认时机。开发中出现以下任一情况时，停止扩张实现：

- 新发现会改变业务结果、权限、计费、数据归属、删除范围或系统边界。
- 实际影响模块、阅读材料或任务包明显超过本期评估。
- 验收链路比计划多出新的环境、迁移或外部依赖。
- 需要用户决策才能选择互斥实现。

暂停时在本期文档填写“阻塞快照”：

```markdown
## 阻塞快照（仅阻塞时填写）
- 已完成：
- 尚未完成：
- 发现的事实与证据：
- 需要用户决定的问题：
- 不同选择的业务影响：
- 当前代码 / 数据是否处于安全状态：
- 恢复开发的第一步：
```

不要在长对话里反复重述全部背景。用户确认后，把决定写回主需求文档和本期交接记录，再继续。

如果实际工作量超过 7 分，停在可验证边界，缩小当前期并把剩余任务拆成新期次。只在缩小后的当前期已经形成独立可验收结果时才把它标记完成；未开始的后续期可以重新编号，已经完成的期次和 Git 标签不得改名或覆盖。

## 七、阶段交接

每期验收后、Git 备份前，在本期文档填写“阶段交接记录”，并把它纳入本期提交：

```markdown
## 阶段交接记录（完成后填写）
- 本期解决的独立问题：
- 已确认的业务事实：
- 关键实现与取舍：
- 变更文件 / 模块：
- 接口、数据结构或配置变化：
- 验收命令与结果：
- 未完成项与明确不做：
- 遗留风险 / 已知问题：
- 下一期开始前必须满足：
- 本期阶段标签：
```

不要在交接记录里写提交号后再制造循环提交；下一期可以通过阶段标签查询精确版本。下一窗口先读上一期交接记录和阶段标签，再读本期核心材料。

## 八、输出前检查

1. 是否先拆任务原子和依赖，再组成期次。
2. 是否给每一期写出六维评分依据，而不是只写“高 / 中 / 低”。
3. 是否存在 8 分以上重期、无理由的 0–3 分轻期，或普通期最高分与最低分相差超过 3。
4. 是否把调研与大量实现、数据迁移与无关功能、旧体系清理与新链路建设塞在同一期。
5. 每期是否只有一个主要问题、3–6 个任务包，并能独立验证。
6. 每期是否有核心必读、按需读取、阻塞快照和阶段交接记录。
7. 下一期是否可以只凭仓库、主需求文档、上期交接和阶段标签继续，不依赖旧聊天上下文。
