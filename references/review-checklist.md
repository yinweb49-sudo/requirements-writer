# 需求文档 / 开发提示词 评审清单

对照模板逐条核对，发现问题就指出位置和改法。带 `{{}}` 的术语按**项目档案**取值；项目没有的机制（多库 / 白名单 / 计费 / 云端层）对应条目跳过，不因缺失判为不合格。

## 业务共识与冲突

- 主需求文档标题后第一节就是“0. 业务需求共识”，没有被背景、架构或技术摘要挤到后面。
- 分别写清用户提出需求的原始目的、最初原始目标、AI 当前理解的最终期望效果；原始目标作为历史记录保留，未被最终方案覆盖。
- 全部使用普通业务语言，能让不了解开发的用户判断“谁使用、从哪里开始、做什么、最后得到什么”；没有用接口、表、字段、服务、队列等术语代替业务结果。
- 多轮沟通中的补充、明确替换和冲突有来源、有影响、有“已确认 / 待确认 / 阻塞确认”状态；只有一轮时明确写“暂无需求演变或冲突”，没有虚构历史。
- 用户没说过的原始目的、业务价值和最终效果未被 AI 擅自补写；技术限制未被当成产品目标。
- 最终期望效果与后续范围、交互、验收和期次一致；不存在前面说一种业务结果、后面按另一种结果开发。
- 会改变使用者、业务结果、主流程、权限、计费、数据归属、删除范围或系统边界的冲突未解决时，没有生成或执行开发期次。

## 范围与过度设计

- 每个产品能力、技术改动、验收项和开发期次都能回指“明确需求”或“必要配套”；必要配套说明缺少它会阻断哪条主链路。
- 没有依据的入口、角色、配置、搜索、筛选、批量、更多输入源、分享、埋点、历史、调度、管理后台和平台扩展未进入本次范围。
- 可选建议与本次交付明确分开，未混入任务清单、数据 / 接口设计、验收标准或期次总览。
- 错误处理、兼容性、可访问性、测试和回归只覆盖本次直接触达的链路，没有借质量要求扩大产品能力或重构无关模块。
- 使用能完成目标的最小闭环；没有为了凑章节、凑期次或匹配模板示例而增加设计。

## 主需求文档
- 结构覆盖本次实际需要的内容；简单需求允许合并或删除不适用章节，不以 11 节齐全为目标。
- 元信息标明业务确认状态；第 0 节给出明确的“可以进入技术设计与分期 / 阻塞确认”结论。
- 有“本次范围与依据”和“明确不做”；范围内每项标明“明确需求 / 必要配套”及依据。
- 关键决策每条有理由；已确认与待确认分开，未验证的不写成结论。
- 架构只展开本次触达的层；涉及密钥时写清归属，密钥不下发到不该有的层。
- 涉及数据变更时，数据模型写清用户隔离与加列 / 建表方式（按 `{{主库}}` / `{{次库}}` 的实际约定）；不涉及时没有新造表或字段。
- 涉及接口变更时，写清鉴权方案（`{{鉴权方案}}`）、白名单（`{{白名单机制}}`，如有）、是否计费；不涉及时没有为实现方便额外新增接口。

## 开发提示词
- 一期一文件；每期含大白话业务目标 / 范围依据 / 动手前必读 / 前置状态 / 任务清单 / 约束 / 验收，数据模型只在实际涉及时展开。
- 每期先读主需求文档第 0 节，业务目标能回指已确认的最终期望效果，没有按过期或冲突版本施工。
- 每期都有范围依据，内容完全来自主需求文档已准入范围；没有可选建议、占位期或“顺手做”的功能。
- 小功能没有机械拆成多期；多期之间存在真实依赖、风险隔离或独立验收价值。
- 每期能独立验收；“重启不丢、按用户隔离”等只在本期实际涉及持久化或用户数据时要求，且明确本期不做什么。
- 引用的需求文档与代码模板路径真实存在。

## 通病
- 无“一律 / 全部”式一刀切；多平台 / 多档位分情况。
- 区分产品能力与实现手段，未把换手段说成砍功能。
- 参考项目 / 竞品的判断有代码 + 行号佐证，非凭 README / 片段。
- 未自创结构，沿用现有目录、命名、组件、端口（以项目档案与仓库现状为准）。
- 未把模板中的示例能力当成默认需求，也未把待确认问题直接排进开发计划。
