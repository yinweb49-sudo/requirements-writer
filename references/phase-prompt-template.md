# 分期开发提示词模板

用这个模板写 `开发提示词/README.md` 和 `期N-*.md`。目标是让每期能单独开窗口执行，AI 读完就知道要看什么、改哪里、不能碰哪里、怎么验收。

> **术语替换（先读）**：占位符 `{{前端}}`、`{{验收方式}}`、`{{结构检索工具}}`、`{{主库}}`、`{{次库}}`、`{{鉴权方案}}`、`{{白名单机制}}` 从**项目档案**取真实值替换；项目没有的机制就删掉对应句子，不硬套。
>
> **范围冻结（必做）**：期次只能拆自主需求文档“本次范围”中已准入的能力。模板出现的输入源、搜索、批量、第三方、体验或平台扩展只是条件说明，不代表要创建对应期次。
>
> **业务共识前置（必做）**：先读主需求文档“0. 业务需求共识”。存在“阻塞确认”时不得生成或执行分期提示词；先回到主需求文档请用户确认。每期业务目标都必须能用大白话回指第 0 节最终期望效果。
>
> **AI 工作量前置（必做）**：生成分期文档前完整读取 `references/phase-workload-planning.md`。先拆任务原子和依赖，再对每期做六维评分与平衡；普通开发期控制在 4–7 分，8 分以上必须继续拆。分期边界首先服务于单窗口工作量、上下文负载、风险隔离和中断恢复，不要求每期都是完整业务功能。
>
> **Git 备份前置（必做）**：生成分期文档前完整读取 `references/git-backup-workflow.md`，现场检查仓库、具名分支、目标远程、远程访问和推送能力，并把脱敏结果写入 README。Git 备份是每期验收后的完成门槛，不单独拆成一期。

## 开发提示词 README

```markdown
# <功能名称> · 分期开发提示词

本目录是“<功能名称>”的分期开发提示词，配合上级目录的《<功能名称>-开发需求文档.md》使用。

## 用法
- 每期单独开一个开发窗口，把对应 `期N-*.md` 的全文作为初始提示词发给 AI。
- 每份提示词都限定核心必读材料、按需材料和一个主要问题，不要求新窗口重新加载全部项目历史。
- 新窗口先读上一期“阶段交接记录”和阶段标签，再读本期核心材料；不得依赖旧窗口的聊天记忆。
- 按数字顺序开发；每期完成并验收通过后，再进入下一期。
- Git 云端备份可用时，只有本期分支提交和阶段标签都推送并验证成功，才算完整完成。

## 期次总览
| 期 | 文档 | 要解决的独立问题 | 工作量 | 上下文 | 依赖 | 独立产物 / 验收 | 阶段标签 | 状态 |
|---|---|---|---:|---|---|---|---|---|

## 工作量平衡结论
- 评分维度：变更面 / 跨层依赖 / 不确定性 / 数据安全风险 / 验收复杂度 / 上下文负载，各 0–2 分。
- 普通开发期目标：4–7 分；本功能普通期范围：<最低分>–<最高分>。
- 8 分以上重期：无 / 有，已拆为 <期次>。
- 0–3 分轻期：无 / 有，已合并到 <期次> / 作为独立检查点保留，理由：<理由>。
- 平衡结论：<为什么不会出现一期过重、后续期次过轻>。

## Git 备份基线

| 项目 | 当前值 |
|---|---|
| 文档生成时检查时间 | YYYY-MM-DD HH:mm（时区） |
| Git 云端备份状态 | 可用 / 写权限待验证 / 不可用 |
| 远程与分支 | <远程名 + 脱敏仓库标识 + 分支；不得含凭据> |
| 远程可见性 | 私有 / 公开 / 未知 |
| 不可用原因 | 无 / <可验证原因> |
| 阶段标签规则 | `backup/<feature-slug>/phase-N` |
| 敏感信息云端备份授权 | 未触发 / 已允许 / 已拒绝 / 已撤销 |
| 授权范围 | 当前仓库 + 当前远程 + 本功能全部期次 |
| 授权时间与依据 | 未触发 / YYYY-MM-DD HH:mm，用户明确回复 |

> 授权状态需要跨开发窗口继承。只有用户主动修改授权，或仓库、远程、可见性变化时才重新确认。

## 全局约束（每期都适用）
- 主需求文档“0. 业务需求共识”是业务基线；技术实现和验收不得改变其中已确认的最终效果。
- 第 0 节出现新的修改或冲突时，先更新并重新确认主需求文档，再继续开发，不按旧提示词自行猜测。
- UI 沿用项目现有设计语言。
- 不复制敏感密钥或连接串。
- 风格、命名、目录结构与现有代码保持一致。
- 只实现主需求文档已准入且分配给本期的能力；不得顺手增加功能、管理入口、配置项、数据记录或后续扩展。
- 发现范围外优化时不要实现，最多在交付说明中标为“可选建议（不纳入本期）”。
- 每期只解决一个主要问题。实际影响面、任务包或阅读材料超过评估时，停在可验证边界并重新拆期，不强行在当前窗口做完。
- 每期完成后填写本期文档的“阶段交接记录”；下一期从持久化代码、文档和阶段标签恢复上下文。
- 涉及本地运行时，优先用项目约定的验收方式（{{验收方式}}）真机 / 真环境验证。
- 每期开始记录起点提交和期初工作区状态；用户原有改动不得覆盖、丢弃或混入本期备份。
- 每期验收通过后按本 README 和本期“Git 备份与回滚”完成敏感信息检查、提交、阶段标签、推送与远程验证。
```

```markdown
## 阻塞与动态拆期
- 新发现改变业务结果、权限、计费、数据归属、删除范围或系统边界时，停止实现并先确认。
- 实际工作量超过 7 分、核心任务包超过 6 个或上下文负载升为“高”时，停在可验证边界并拆分剩余任务。
- 只有缩小后的本期已经形成独立可验收结果，才能标记完成；不得为了保持原期数硬做完。
- 已完成期次和 Git 标签不改名、不覆盖；未开始期次可根据新依赖重新编号。

## Git 备份与回滚（验收通过后必做）
1. 重新检查 Git 云端备份状态：
   - README 已标记“不可用”且现场仍不可用：记录“本期未执行云端备份”和原因，跳过后续备份步骤；可以交付开发结果，但不得声称已有云端恢复点。
   - 状态为“可用 / 写权限待验证”：继续执行下列步骤。
2. 检查本期待提交文件和待推送提交是否含密钥、密码、令牌、私钥、带口令连接串等敏感信息；只报告路径和类型，不展示具体值。
3. 检出敏感信息时读取 README 的授权状态：
   - “未触发”：暂停提交与推送，说明远程可见性和 Git 历史泄露风险，只询问一次是否允许上传。
   - “已允许”：直接继续，不重复询问。
   - “已拒绝 / 已撤销”：不得上传敏感文件；先排除或脱敏，再备份安全改动。
   - 仓库、远程或可见性变化：旧授权失效，重新确认。
4. 授权状态发生变化时，在提交前更新 README 的授权状态和依据，不记录任何敏感值；备份结果以远程标签和交付报告为准，不为回写提交号或“已推送”状态制造循环提交。
5. 使用动手前已经记录的 `BASE_SHA` 和期初工作区清单核对变更，不得到收尾时才重新计算起点；只按明确文件路径暂存本期改动，禁止 `git add .` / `git add -A`。
6. 创建提交 `backup(<feature-slug>): phase N complete`，创建不可覆盖的阶段标签 `backup/<feature-slug>/phase-N`，推送分支和标签并验证远程均已存在。
7. 同名标签指向其他提交时不得移动或覆盖，改用 `backup/<feature-slug>/phase-N-r2` 等递增标签。
8. 交付报告必须给出验收结果、分支、完整提交号、阶段标签、推送结果，以及未备份文件和原因。
9. 原本可用但推送失败时标记“开发验收通过，云端备份失败”，不得宣称本期完整完成，也不得用强推绕过问题。

安全回看阶段版本时，使用 `git switch -c rollback/<feature-slug>-phase-N backup/<feature-slug>/phase-N` 新建分支；除非用户明确授权，不使用 `git reset --hard` 或强推。
```

## 期次拆分方法

先确认主需求文档第 0 节不存在“阻塞确认”，再按范围准入过滤，最后按 `references/phase-workload-planning.md` 拆任务原子、画依赖、评分和平衡。

- 分期首先服务于 AI 单窗口执行，不要求每期都是完整业务功能。
- 普通开发期控制在 4–7 分；8 分以上强制拆，0–3 分轻量期原则上合并或写明独立检查点理由。
- 同一业务能力可以拆成多个关联技术问题；不要按前端 / 后端 / 数据库机械拆，也不要把调研、大量实现、迁移和清理塞进同一期。
- 每期只有一个主要问题、3–6 个核心任务包，并留下可验证产物和阶段交接。
- Git 检查、敏感信息检查、提交、标签和推送属于每期完成门槛，不创建“Git 备份期”。
- 只有需求已确认删除旧体系时才单独创建清理期，并放在新链路稳定之后。
- 体验、更多输入源、识别、搜索、第三方、批量、横向平台等只有在主需求文档已准入时才能成为期次。
- 不创建“以后也许会做”的占位期；可选建议不进入期次总览。

## 必写边界

- 本期不做什么。
- 哪些旧功能不能碰。
- 哪些新功能必须回归。
- 涉及密钥 / 配置时，写清不能进入哪些层。
- 涉及新增接口时，写清是否加入运行档位白名单（`{{白名单机制}}`；无此机制则忽略）。
- 涉及计费时，写清哪些行为计费或不计费。
- 涉及用户数据时，写清如何按当前用户隔离。
- 写清六维工作量评分、上下文边界、预计阻塞点、动态拆期条件和阶段交接。
- 写清 Git 云端备份状态、阶段标签、敏感信息授权状态和备份失败时的停止条件。

## 不同类型期次的额外要求

只有主需求文档已确认存在对应类型的工作时，才使用下面的小节；小节标题本身不是创建该期次的理由。

### 调研 / 业务确认期（不确定性为 2 时）

- 只在错误理解现状会直接导致返工时创建，不为简单任务增加空泛调研期。
- 产出现状地图、代码 / 数据证据、关键业务规则、待用户确认点和后续开发入口。
- 不在结论未确认时顺手实现某个分支。
- 验收是“证据和决策足以让下一期不依赖旧聊天继续”，不是提交大量代码。

### 数据地基期（涉及数据变更时）

- 写本期实际涉及的实体、数据上下文、建表脚本、索引、可空字段和用户隔离。
- 只有本期确实需要对外提供数据能力时才写 Controller、Service 和 API 封装。
- 涉及持久化时验收“重启后数据不丢”；涉及多用户数据时验收“换账号只看自己的数据”。

### 云端或第三方期（已确认涉及时）

- 写密钥只在云端 / 服务端。
- 本期存在跨层调用时，写调用方经现有鉴权通道（`{{鉴权方案}}`）访问。
- 按实际链路写同步 / 异步和失败状态，不为模板新增异步机制。
- 写接口调研结论；未实测就写开发前需确认。

### 批量 / 搜索期（已确认涉及时）

- 只有存在“先预览再选择”的已确认流程时，才写候选数据是否落库。
- 只有数据规模或接口约束确实需要时，才写分页 / 游标 / 去重 / 上限。
- 涉及批量处理时，写单条失败是否影响整批。
- 涉及候选外链时，复用项目已有打开方式。

### 清理旧体系期（已确认删除时）

- 先列“必须保留”。
- 再列“删除清单”，按后端、前端、表、脚本、文档分组。
- 要求用 {{结构检索工具}} / 搜索核对依赖，分批删、边删边编译。
- 验收必须包含新链路回归和旧引用全局搜索。

### 体验打磨期（已确认且需独立验收时）

- 只写范围表中已确认的体验项，按价值排序。
- 不引入新链路。
- 验收只覆盖本期实际改变的页面状态和交互，不顺带增加编辑、批量、筛选或分页。
