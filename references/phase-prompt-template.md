# 分期开发提示词模板

用这个模板写 `开发提示词/README.md` 和 `期N-*.md`。目标是让每期能单独开窗口执行，AI 读完就知道要看什么、改哪里、不能碰哪里、怎么验收。

> **术语替换（先读）**：占位符 `{{前端}}`、`{{验收方式}}`、`{{结构检索工具}}`、`{{主库}}`、`{{次库}}`、`{{鉴权方案}}`、`{{白名单机制}}` 从**项目档案**取真实值替换；项目没有的机制就删掉对应句子，不硬套。
>
> **范围冻结（必做）**：期次只能拆自主需求文档“本次范围”中已准入的能力。模板出现的输入源、搜索、批量、第三方、体验或平台扩展只是条件说明，不代表要创建对应期次。
>
> **业务共识前置（必做）**：先读主需求文档“0. 业务需求共识”。存在“阻塞确认”时不得生成或执行分期提示词；先回到主需求文档请用户确认。每期业务目标都必须能用大白话回指第 0 节最终期望效果。

## 开发提示词 README

```markdown
# <功能名称> · 分期开发提示词

本目录是“<功能名称>”的分期开发提示词，配合上级目录的《<功能名称>-开发需求文档.md》使用。

## 用法
- 每期单独开一个开发窗口，把对应 `期N-*.md` 的全文作为初始提示词发给 AI。
- 每份提示词都包含“动手前必读”清单，AI 需先读需求文档与现有代码模板。
- 按数字顺序开发；每期完成并验收通过后，再进入下一期。

## 期次总览
| 期 | 文档 | 一句话 |
|---|---|---|

## 全局约束（每期都适用）
- 主需求文档“0. 业务需求共识”是业务基线；技术实现和验收不得改变其中已确认的最终效果。
- 第 0 节出现新的修改或冲突时，先更新并重新确认主需求文档，再继续开发，不按旧提示词自行猜测。
- UI 沿用项目现有设计语言。
- 不复制敏感密钥或连接串。
- 风格、命名、目录结构与现有代码保持一致。
- 只实现主需求文档已准入且分配给本期的能力；不得顺手增加功能、管理入口、配置项、数据记录或后续扩展。
- 发现范围外优化时不要实现，最多在交付说明中标为“可选建议（不纳入本期）”。
- 涉及本地运行时，优先用项目约定的验收方式（{{验收方式}}）真机 / 真环境验证。
```

## 单期提示词结构

每份 `期N-*.md` 按下面结构写：

```markdown
# 期N 开发提示词 · <期次名称>

你是本项目的开发工程师。本期目标：<一句话说清本期闭环>。<明确不做什么、依赖什么、业务价值是什么>。

## 本期业务目标（大白话）
<不用开发术语说明：本期完成后，谁可以在哪里做什么，会看到或得到什么结果；对应主需求文档 §0 的哪一项最终效果。>

## 范围依据
- 明确需求：<对应主需求文档范围表中的条目>
- 必要配套：<如有，说明缺少它会阻断哪条主链路；没有则写“无”>
- 本期不做：<列出容易被误加、但未准入或属于其他期次的内容>

## 动手前必读
1. 需求文档：`docs/<功能>/<功能>-开发需求文档.md`，先读 §0“业务需求共识”，再读本期对应章节。
2. 前期成果：<期1 / 期2 已完成的关键代码或能力>。
3. 现有代码模板：
   - <前端页面 / API>
   - <后端 Controller / Service / Entity>
   - <鉴权 / 白名单 / 打包脚本>

## 前置状态
<写清本期开始前系统应处于什么状态，以及本期不能破坏哪些已完成能力。>

## 任务清单

只保留本期实际涉及的层；不涉及的层不要为凑结构创建任务。

### <实际涉及的页面 / 服务 / 数据层>
1. <具体到文件、类、接口、字段、行为>

## 数据模型（涉及时）
<涉及则写实际变更；不涉及可省略，或一句话写“复用已有数据，无需改结构”。>

## 技术约束与边界
- <只写与本期实际任务相关的计费、密钥、旧代码、数据库等边界>
- <只写本期实际存在的失败、并发、异步或容量边界>
- <搜索、筛选、批量、外链、上传、分页等未准入时不得加入>

## 验收
用 {{验收方式}} 起本地环境：
1. <用户从页面入口开始的步骤>
2. <成功状态>
3. <失败 / 异常状态>
4. <下游链路或回归验证>
```

## 期次拆分方法

先确认主需求文档第 0 节不存在“阻塞确认”，再按范围准入结果过滤，最后按“风险从低到高、闭环从小到大”拆。

- 小功能能一次完成并验收时只写一期，不按前端 / 后端 / 数据层机械拆期。
- 多期只用于已确认能力之间的真实依赖、风险隔离或独立验收；每期内容都能回指主需求文档范围表。
- 只有需求已确认删除旧体系时才单独创建清理期，并放在新链路稳定之后。
- 体验、更多输入源、识别、搜索、第三方、批量、横向平台等只有在主需求文档已准入时才能成为期次。
- 不创建“以后也许会做”的占位期；可选建议不进入期次总览。

## 必写边界

- 本期不做什么。
- 哪些旧功能不能碰。
- 哪些新功能必须回归。
- 涉及密钥 / 配置时，写清不能进入哪些层。
- 涉及新增接口时，写清是否加入运行档位白名单（`{{白名单机制}}`；无此机制则忽略）。
- 涉及计费时，写清哪些行为计费或不计费。
- 涉及用户数据时，写清如何按当前用户隔离。

## 不同类型期次的额外要求

只有主需求文档已确认存在对应类型的工作时，才使用下面的小节；小节标题本身不是创建该期次的理由。

### 数据地基期（涉及数据变更时）

- 写本期实际涉及的实体、数据上下文、建表脚本、索引、可空字段和用户隔离。
- 只有本期确实需要对外提供数据能力时才写 Controller、Service 和 API 封装。
- 涉及持久化时验收“重启后数据不丢”；涉及多用户数据时验收“换账号只看自己的数据”。

### 云端或第三方期（已确认涉及时）

- 写密钥只在云端 / 服务端。
- 本期存在跨层调用时，写调用方经现有鉴权通道（`{{鉴权方案}}`）访问。
- 按实际链路写同步 / 异步和失败状态，不为模板新增异步机制。
- 写接口调研结论；未实测就写开发前需确认。

### 批量 / 搜索期（已确认涉及时）

- 只有存在“先预览再选择”的已确认流程时，才写候选数据是否落库。
- 只有数据规模或接口约束确实需要时，才写分页 / 游标 / 去重 / 上限。
- 涉及批量处理时，写单条失败是否影响整批。
- 涉及候选外链时，复用项目已有打开方式。

### 清理旧体系期（已确认删除时）

- 先列“必须保留”。
- 再列“删除清单”，按后端、前端、表、脚本、文档分组。
- 要求用 {{结构检索工具}} / 搜索核对依赖，分批删、边删边编译。
- 验收必须包含新链路回归和旧引用全局搜索。

### 体验打磨期（已确认且需独立验收时）

- 只写范围表中已确认的体验项，按价值排序。
- 不引入新链路。
- 验收只覆盖本期实际改变的页面状态和交互，不顺带增加编辑、批量、筛选或分页。
