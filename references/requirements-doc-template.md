# 功能开发需求文档模板

用这个模板写“主需求文档”。目标是让后续开发 AI 看到文档后，能按项目现状施工，而不是重新发明需求结构。

> **术语替换与裁剪（先读）**
> 本模板按“多层架构 + 多数据库 + 云端密钥 + 计费 / 白名单”的最复杂情形给结构。写文档时：
> - 占位符 `{{前端}}`、`{{本地后端}}`、`{{云端后端}}`、`{{主库}}`、`{{次库}}`、`{{鉴权方案}}`、`{{白名单机制}}`、`{{结构检索工具}}` 从**项目档案**取真实名替换。
> - 项目档案里没有的层 / 库 / 机制，直接删掉对应小节，别为凑结构硬造需求。单体项目就写单层，无云端就不写云端，无计费就写“不计费”。

## 标题与元信息

```markdown
# <项目名> · <功能名称> 开发需求文档

- 文档版本：v0.1（待评审）
- 编写日期：YYYY-MM-DD
- 适用范围：
  - 前端 {{前端}}
  - 本地后端 {{本地后端}}（如有）
  - 云端后端 {{云端后端}}（如涉及）
- 参考来源：<用户材料 / 现有代码 / 外部接口 / 旧功能>
```

## 1. 背景与目标

写清三件事：

- 现状：现在用户怎么做、哪里慢、哪里错、哪里成本高、哪些旧链路要弃用。
- 目标：重构或新建后，用户能完成什么闭环。
- 原则：UI 风格、数据归属、计费、复用现有能力、不要自造链路等。

示例结构：

```markdown
## 1. 背景与目标

### 1.1 现状（要保留 / 要弃用）
### 1.2 重构目标
### 1.3 设计原则
```

## 2. 关键决策

把已经确认的产品 / 技术选择写成表格。每条都要有“理由”，避免后续 AI 改写成另一个方案。

```markdown
## 2. 关键决策（已与产品确认）

| # | 决策点 | 结论 | 理由 |
|---|---|---|---|
| 1 | <例如密钥放哪里> | <云端 / 本地> | <避免下发到用户电脑，便于统一成本控制> |
```

没有确认的内容不要放这里，单独放“待确认问题”。

## 3. 整体架构

按项目真实运行档位写，不要只画单体架构（除非项目本就是单体，则如实写单层）。

```markdown
## 3. 整体架构

### 3.1 分层拓扑
{{前端}} -> {{本地后端}} -> {{云端后端}}
（层数按项目档案；单体只写一层，两层就写两层，不硬套三层）

### 3.2 业务链路
用文本流程图写主链路、补充链路、异步链路、失败链路。
```

必须说明（按实际存在的层）：

- 前端是否直连外部域名。
- 本地后端负责哪些本地数据和任务。
- 云端负责哪些密钥、第三方调用、计费或账号能力。
- 异步任务由 worker / HostedService / 队列负责，还是同步返回。

## 4. 功能与交互设计

面向用户写页面如何变化。不要只写接口。

建议覆盖：

- 页面入口、主操作区、次级按钮、弹窗。
- 列表 / 表格列、状态标签、操作按钮。
- 空状态、失败提示、加载态、批量操作。
- 新功能如何进入现有下游链路。

```markdown
## 4. 功能与交互设计

### 4.1 <主入口 / 主流程>
### 4.2 <列表 / 结果区>
### 4.3 空状态与反馈
```

## 5. 复用与弃用清单

明确哪些复用、哪些替换、哪些不能误删。涉及旧系统清理时必须写。

```markdown
## 5. 复用与弃用清单

### 5.1 复用
| 模块 | 文件 / 能力 | 用途 |

### 5.2 替换
- <页面 / 接口 / 服务>

### 5.3 清理
- 删除前先用 {{结构检索工具}} / 搜索核对依赖。
- 列出后端、前端、表结构、脚本、文档同步项。

### 5.4 必须保留
- <新链路依赖>
- <下游功能>
```

## 6. 数据模型设计

主库默认 `{{主库}}`；如有次库 `{{次库}}`，写清是否需要两边都改。

必须覆盖：

- 新增表或新增字段。
- 字段含义、枚举取值、索引、唯一约束。
- 用户隔离字段（项目档案里登记的隔离字段，如 `OwnerType` / `UID`）。
- 加列 / 建表约定（按项目档案，如幂等建表或 `ALTER ADD COLUMN`、迁移工具用法）。
- 多库差异（如唯一索引对多 NULL 的处理、过滤索引等）。
- 是否有生产数据迁移；没有证据时写“需确认”。

## 7. 接口设计

按项目档案里的层分开写（有几层写几段）。

```markdown
## 7. 接口设计

### 7.1 {{本地后端}} 新增
| 方法 | 路径 | 入参 | 返回 | 说明 |

### 7.2 {{云端后端}} 新增（如涉及）
| 方法 | 路径 | 入参 | 返回 | 说明 |

### 7.3 鉴权与计费
```

必须说明：

- Controller / 路由放哪个目录。
- 用 `{{鉴权方案}}` 里的哪种（从项目档案取，如某种 scheme / JWT / 单一鉴权）。
- 是否需要加入 `{{白名单机制}}`（如按运行档位暴露控制器的白名单；无此机制则删掉）。
- 是否计费；如果不计费，明确“不接入计费”。
- 幂等、重试、异步状态、失败原因。

## 8. 技术选型或第三方接口

只有在确实涉及新库、模型、第三方平台时写。格式要可验证：

- 选型结论。
- 为什么这样选。
- 依赖体积、打包、权限、成本。
- 调研日期、接口路径、请求方式、关键参数、返回字段。
- 易踩坑。

没有实测的接口写“需开发前调研”，不要写成已实测。

## 9. 分期开发计划

每期必须能独立验收。常见拆法：

1. 期1：数据层 + 最小闭环，先跑通“输入 -> 列表 -> 入下游”。
2. 期2：本地补充能力或核心子能力。
3. 期3：云端 / 第三方主链路。
4. 期4：旧体系清理，必须等新链路跑通后再删。
5. 期5：体验打磨。
6. 后续期：横向平台、批量能力、扩展能力。

```markdown
| 期 | 名称 | 核心内容 | 依赖 | 验收 |
|---|---|---|---|---|
```

## 10. 已确认决策

用日期固化容易被误改的结论，例如：

- 是否计费。
- 密钥归属。
- 是否允许改数据库结构。
- 是否清理旧系统。
- 用户隔离要求。

## 11. 风险与对策

至少覆盖：

- 第三方服务失败或成本风险。
- 异步任务重启 / 卡状态风险。
- 删除旧代码的连带影响。
- 数据库索引 / 迁移风险。
- 前端体验和异常输入风险。

## 待确认问题

只有确实没证据时添加。不要为了显得完整而阻塞明确需求。

```markdown
## 待确认问题

1. <问题>：影响 <范围>，建议确认 <选项A / 选项B>。
```
