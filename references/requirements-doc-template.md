# 功能开发需求文档模板

用这个模板写“主需求文档”。目标是让后续开发 AI 看到文档后，能按项目现状施工，而不是重新发明需求结构。

> **术语替换与裁剪（先读）**
> 本模板按“多层架构 + 多数据库 + 云端密钥 + 计费 / 白名单”的最复杂情形给结构。写文档时：
> - 占位符 `{{前端}}`、`{{本地后端}}`、`{{云端后端}}`、`{{主库}}`、`{{次库}}`、`{{鉴权方案}}`、`{{白名单机制}}`、`{{结构检索工具}}` 从**项目档案**取真实名替换。
> - 项目档案里没有的层 / 库 / 机制，直接删掉对应小节，别为凑结构硬造需求。单体项目就写单层，无云端就不写云端，无计费就写“不计费”。
> - 模板列举的是检查维度，不是默认功能清单。只有“用户 / 现有材料已确认”或“主链路不可缺少的必要配套”才能写入本次功能、任务、验收和期次。
> - 简单需求可以合并或删除不适用章节；某类技术不涉及时，一句话写“不涉及 / 保持不变”，不要为了补齐 11 节设计新接口、新表或新流程。
> - 无论需求大小，标题后面的“0. 业务需求共识”都不能删除或移到技术章节之后。它是给用户确认 AI 是否理解正确的，不是写给开发人员看的技术摘要。

## 标题与元信息

```markdown
# <项目名> · <功能名称> 开发需求文档

- 文档版本：v0.1（待评审）
- 编写日期：YYYY-MM-DD
- 适用范围：
  - 前端 {{前端}}
  - 本地后端 {{本地后端}}（如有）
  - 云端后端 {{云端后端}}（如涉及）
- 参考来源：<用户材料 / 现有代码 / 外部接口 / 旧功能>
- 业务确认状态：待确认 / 已确认（YYYY-MM-DD）/ 阻塞确认
```

## 0. 业务需求共识（开头必写）

本节只用普通人能听懂的业务语言。不要出现类名、方法名、表名、字段名、API 路径、队列等开发术语；确实需要提及时，先说用户能感知的影响，再在括号里补技术名。

明确区分：

- **原始目的**回答“为什么要做、想解决什么问题”。
- **原始目标**回答“用户最开始想做到什么”。
- **最终期望效果**回答“经过多轮沟通后，AI 当前理解为最终要交付什么”。
- 原始目标保留为历史记录，不能被最终方案覆盖或改写。

```markdown
## 0. 业务需求共识（请先确认）

### 0.1 一句话大白话
<谁在什么场景遇到什么问题，希望通过本功能完成什么，最后得到什么结果。>

### 0.2 用户提出需求的原始目的
- 想解决的问题：<用户为什么提出需求；未说明就写“未明确说明，待确认”>
- 业务价值：<省时间、减少错误、降低成本、完成某项业务等；没有依据不要编造>

### 0.3 用户最开始提出的原始目标
- 使用者：<谁使用>
- 原始操作与结果：<用户最初希望怎么做、得到什么>
- 原始明确边界：<最开始明确不要什么；没有则写“未明确”>

### 0.4 AI 当前理解的最终期望效果
- 使用者最终从哪里开始：<页面 / 业务入口，用业务名称>
- 用户要做什么：<关键动作>
- 系统最后给用户什么结果：<用户能看到、拿到或继续完成什么>
- 哪些现有业务保持不变：<与本次直接相关的保留项>
- 明确不包含：<已经确认不做的能力>

### 0.5 多轮沟通中的需求演变与冲突
| 轮次 / 来源 | 当时的说法或目标 | 变化类型 | 对最终效果的影响 | 确认状态 |
|---|---|---|---|---|
| 初始需求 | <原始目标> | 原始版本 | <作为对照基线> | 已记录 |
| 后续沟通 | <补充或不同说法> | 补充 / 明确替换 / 冲突 | <最终增加、取消或尚不确定什么> | 已确认 / 待确认 / 阻塞确认 |

没有演变或冲突时明确写：“当前需求与原始目标一致，暂无需求演变或冲突。”

### 0.6 请用户确认
- 当前理解是否就是你最终想要的业务效果：是 / 否 / 待确认
- 是否仍有未解决冲突：无 / 有，见上表
- 结论：可以进入技术设计与分期 / 存在阻塞确认，暂不拆分开发期次
```

判断规则：

- 用户明确说“改为 / 取消 / 以新方案为准”时，可以把后续说法标为“明确替换”，但仍保留原始目标。
- 后续说法只是设想、语气不确定，或同时保留两种互斥结果时，标为“待确认 / 阻塞确认”，不要替用户选。
- 会改变使用者、业务结果、主流程、权限、计费、数据归属、删除范围或系统边界的冲突未解决时，后续技术章节只能写草案，分期开发计划写“待业务共识确认后再拆分”。
- 只有当前一轮材料时也要写本节，并明确“暂无需求演变或冲突”；不要为了填表虚构历史。

## 1. 背景与目标

这一节承接第 0 节，不得重新解释成不同的业务目标。写清：

- 现状：现在用户怎么做、哪里慢、哪里错、哪里成本高、哪些旧链路要弃用。
- 目标：重构或新建后，用户能完成什么闭环。
- 范围：哪些能力纳入本次，依据是什么；哪些明确不做。
- 原则：UI 风格、数据归属、计费、复用现有能力、不要自造链路等，只写与本次相关的约束。

示例结构：

```markdown
## 1. 背景与目标

### 1.1 现状（要保留 / 要弃用）
### 1.2 重构目标
### 1.3 本次范围与依据
| 能力 / 改动 | 准入类型 | 依据 |
|---|---|---|
| <功能点> | 明确需求 / 必要配套 | <用户原话、文档、代码事实，或缺少它为何无法完成主链路> |

### 1.4 明确不做
### 1.5 设计原则
```

“可选建议”如确有价值，单独放在文末并标注“不纳入本次”；不要把它写入范围表、开发计划或验收标准。

## 2. 关键决策

把已经确认的产品 / 技术选择写成表格。每条都要有“依据”和“理由”，避免后续 AI 把推测写成结论或改写成另一个方案。

```markdown
## 2. 关键决策（已与产品确认）

| # | 决策点 | 结论 | 依据 | 理由 |
|---|---|---|---|---|
| 1 | <例如密钥放哪里> | <云端 / 本地> | <用户确认 / 现有代码> | <避免下发到用户电脑，便于统一成本控制> |
```

没有确认的内容不要放这里，单独放“待确认问题”。

## 3. 整体架构

按项目真实运行档位写，不要只画单体架构（除非项目本就是单体，则如实写单层）。

```markdown
## 3. 整体架构

### 3.1 分层拓扑
{{前端}} -> {{本地后端}} -> {{云端后端}}
（层数按项目档案；单体只写一层，两层就写两层，不硬套三层）

### 3.2 业务链路
用文本流程图写主链路，以及本次确实涉及的失败 / 异步 / 补充链路。
```

按本次实际触达的层说明：

- 涉及外部调用时，前端是否直连外部域名。
- 涉及本地后端时，它负责哪些本地数据和任务。
- 涉及云端时，它负责哪些密钥、第三方调用、计费或账号能力。
- 涉及耗时或异步任务时，由 worker / HostedService / 队列负责，还是同步返回。

## 4. 功能与交互设计

面向用户写页面如何变化。不要只写接口。

按本次范围选择覆盖：

- 实际新增或变化的页面入口、操作区、按钮和弹窗。
- 实际变化的列表 / 表格列、状态标签和操作按钮。
- 主链路会遇到的加载、成功、失败和无结果状态。
- 新功能如何进入已确认的现有下游链路。
- 搜索、筛选、批量、分页、上传、外链等只有在范围表已准入时才写。

```markdown
## 4. 功能与交互设计

### 4.1 <主入口 / 主流程>
### 4.2 <列表 / 结果区>
### 4.3 空状态与反馈
```

## 5. 复用与弃用清单

明确哪些复用、哪些替换、哪些不能误删。没有替换或清理时简要写“保持不变”；只有已确认要清理旧系统时才展开删除清单。

```markdown
## 5. 复用与弃用清单

### 5.1 复用
| 模块 | 文件 / 能力 | 用途 |

### 5.2 替换
- <页面 / 接口 / 服务>

### 5.3 清理
- 删除前先用 {{结构检索工具}} / 搜索核对依赖。
- 列出后端、前端、表结构、脚本、文档同步项。

### 5.4 必须保留
- <新链路依赖>
- <下游功能>
```

## 6. 数据模型设计

主库默认 `{{主库}}`；如有次库 `{{次库}}`，写清是否需要两边都改。

不涉及数据结构时，直接写“复用现有数据，无需改表 / 字段 / 索引 / 迁移”，不要为功能增加记录表、历史表、配置表或埋点字段。

涉及数据结构时才覆盖：

- 新增表或新增字段。
- 字段含义、枚举取值、索引、唯一约束。
- 用户隔离字段（项目档案里登记的隔离字段，如 `OwnerType` / `UID`）。
- 加列 / 建表约定（按项目档案，如幂等建表或 `ALTER ADD COLUMN`、迁移工具用法）。
- 多库差异（如唯一索引对多 NULL 的处理、过滤索引等）。
- 是否有生产数据迁移；没有证据时写“需确认”。

## 7. 接口设计

不涉及接口变更时，直接写“复用现有接口，无新增 / 修改”，不要为方便实现额外设计接口。涉及接口时，按本次实际触达的层分开写。

```markdown
## 7. 接口设计

### 7.1 {{本地后端}} 新增
| 方法 | 路径 | 入参 | 返回 | 说明 |

### 7.2 {{云端后端}} 新增（如涉及）
| 方法 | 路径 | 入参 | 返回 | 说明 |

### 7.3 鉴权与计费
```

新增或修改接口时说明：

- Controller / 路由放哪个目录。
- 用 `{{鉴权方案}}` 里的哪种（从项目档案取，如某种 scheme / JWT / 单一鉴权）。
- 是否需要加入 `{{白名单机制}}`（如按运行档位暴露控制器的白名单；无此机制则删掉）。
- 是否计费；如果不计费，明确“不接入计费”。
- 只有相关时才写幂等、重试、异步状态和失败原因；不要为满足模板引入异步或重试机制。

## 8. 技术选型或第三方接口

只有在确实涉及新库、模型、第三方平台时写。格式要可验证：

- 选型结论。
- 为什么这样选。
- 依赖体积、打包、权限、成本。
- 调研日期、接口路径、请求方式、关键参数、返回字段。
- 易踩坑。

没有实测的接口写“需开发前调研”，不要写成已实测。

## 9. 分期开发计划

先检查第 0 节业务确认状态：存在“阻塞确认”时，不拆期，只写“待业务共识确认后再拆分”。业务共识可进入开发后，按 `references/phase-workload-planning.md` 规划期次。

**分期首先服务于 AI 的执行稳定性，不是按业务功能机械分组。** 同一项业务能力可以拆成多个技术执行期；一期也可以只完成调研证据、稳定契约、风险隔离或迁移验证，只要它解决独立问题、有持久化产物并能独立核对。

拆期顺序：

1. 从已准入范围中列出调研、确认、设计、代码、数据、测试、迁移、清理等任务原子。
2. 标记依赖、未知信息、风险、影响模块和验收方式，先画单向依赖再组合期次。
3. 给每个候选期次做六维评分：变更面、跨层依赖、不确定性、数据 / 安全风险、验收复杂度、上下文负载，各 0–2 分。
4. 普通开发期控制在 4–7 分；8 分以上必须继续拆；多期中的 0–3 分轻量期原则上并入相邻期，独立调研 / 确认、高风险迁移或清理检查点可写明理由后保留。
5. 普通开发期最高分与最低分差不超过 3。不要出现前一期承担绝大多数开发，后几期只剩零碎补丁。
6. 每期只解决一个主要问题，安排 3–6 个核心任务包，完成后保持可构建、可验证、可继续开发。
7. 已确认的旧体系清理放在新链路跑通后；可选优化和未来设想不能用于平衡分数或凑期次。

评分覆盖读取核心材料、理解业务、实现、验收、交接和备份的整期负担，不只看代码量；它用于衡量 AI 单窗口负担，不是开发工时。不要写“预计几小时 / 几天”代替工作量依据。

```markdown
### 9.1 分期工作量评估

评分缩写：变更面 / 跨层依赖 / 不确定性 / 数据安全风险 / 验收复杂度 / 上下文负载。

| 期 | 要解决的独立问题 | 六维评分 | 总分 | 上下文负载 | 拆分 / 合并结论 |
|---|---|---|---:|---|---|
| 期1 | <问题，不写笼统业务模块名> | 1 / 1 / 1 / 0 / 1 / 1 | 5 | 中 | 保留：负载在目标区间 |

平衡结论：
- 普通开发期分数范围：<最低分>–<最高分>
- 是否存在 8 分以上重期：无 / 有，已继续拆为 <期次>
- 是否存在无理由的 0–3 分轻期：无 / 有，已合并到 <期次>
- 是否需要独立调研 / 确认期：否 / 是，理由与产物为 <内容>
```

需要同时输出分期开发提示词时，按 `references/git-backup-workflow.md` 现场检查 Git 云端备份条件，并在本节写一段脱敏摘要：

```markdown
### 9.2 Git 备份基线
- 检查结果：可用 / 写权限待验证 / 不可用
- 目标远程与分支：<远程名 + 脱敏仓库标识 + 分支，不写含凭据 URL>
- 远程可见性：私有 / 公开 / 未知
- 分期完成门槛：每期验收通过后完成敏感信息检查、阶段提交、不可覆盖标签、分支与标签推送验证
- 详细状态与一次性敏感信息上传授权：见 `开发提示词/README.md`
```

Git 备份是开发保障，不是产品能力；不加入“本次范围与依据”，不创建独立期次。Git 不可用时只记录原因，不自动创建仓库、连接远程或索要凭据。

```markdown
### 9.3 期次计划

| 期 | 名称 | 独立问题与核心任务包 | 范围依据 | 工作量 | 依赖 / 输入 | 独立产物与验收 |
|---|---|---|---|---:|---|---|
```

## 10. 已确认决策

用日期固化容易被误改的结论，例如：

- 第 0 节最终期望效果是否已经由用户确认。
- 是否计费。
- 密钥归属。
- 是否允许改数据库结构。
- 是否清理旧系统。
- 用户隔离要求。

## 11. 风险与对策

只列与本次变更直接相关、确有依据的风险，不按类别凑数量。例如：

- 确实调用第三方服务时，写失败或成本风险。
- 确实存在异步任务时，写重启 / 卡状态风险。
- 确实删除旧代码时，写连带影响。
- 确实变更数据库时，写索引 / 迁移风险。
- 本次交互直接触达的异常输入和前端反馈风险。

## 待确认问题

只有确实没证据且答案会影响本次方案时添加。不要为了显得完整而阻塞明确需求，也不要把可选扩展包装成待确认问题。

```markdown
## 待确认问题

1. <问题>：影响 <范围>，建议确认 <选项A / 选项B>。
```
